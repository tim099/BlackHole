# 黑洞模擬 —— 設計、驗證、預留

一個不用安裝、不用架伺服器的網頁：`index.html` 直接點兩下就開（需要支援 WebGL2 的瀏覽器）。

打開先到主選單，兩個模式：**黑洞模擬**（下面這些）與**太空戰鬥**（第 8 節）。背景的星空是真的星表（第 9 節）。

黑洞模擬的場景（另外還有 ④ 飛船，見 README）：

| 場景 | 看什麼 |
|---|---|
| ① 光線彎曲 | 黑洞的影子、被彎到上面來的吸積盤背面、右下角俯視圖上一排平行光各自怎麼彎 |
| ② 物體掉入 | 把發光的立方體（或球）、光束丟進去：速度、方向、質量、形狀都可調；遠處看到它變慢、變紅、變暗、停在視界前 |
| ③ 自己掉入 | 攝影機自由落下，穿過視界，一路算到 0.02 rs；可以轉頭看外面 |

操作：滑鼠拖曳＝繞著黑洞轉（落下時＝轉頭）、Shift 或右鍵拖曳＝轉頭、滾輪＝遠近（落下時＝視角）、按兩下＝看回黑洞；
空白鍵暫停、`1` `2` `3` 換場景、`L` 發射、`F` 落下、`H` 懸停。在右下角俯視圖上按住拖曳＝彈弓發射。

單位：長度是黑洞的史瓦西半徑 rs，時間是 rs/c。「顯示 → 換算成」可以選黑洞的質量，讀數會多出公里、秒，以及潮汐力。

## 1. 檔案

```
index.html      版面與樣式
js/physics.js   物理核心：度規、運動方程式、積分、標架（瀏覽器與 node 共用，不碰畫面）
js/selftest.js  物理核心的自我測試（node js/selftest.js）
js/shader.js    著色器：每個像素往回追一條光線
js/renderer.js  WebGL2：把「畫面描述」交給著色器
js/camera.js    觀察者：懸停／自由落下／到奇異點
js/bodies.js    拋進去的東西：軌跡、看到的位置、交給著色器的資料
js/map2d.js     右下角的俯視圖
js/app.js       介面、場景、畫面迴圈、用顯示卡算的自我測試
js/ship.js、js/ship_data.js    飛船模型（雕刻作品的格子）與它的求交
js/stars.js、js/stars_data.js  星表（第 9 節）
js/game.js、js/world.js、js/gameui.js  太空戰鬥模式（第 8 節）
tools/serve.py       開發用的本機伺服器（不快取）。平常用不到。
tools/ship_pack.py、tools/stars_pack.py  把雕刻作品／星表轉成上面那兩個資料檔
```

分層的原則：**物理只寫在 `physics.js` 與 `shader.js` 兩個地方**（同一組方程式各一份，CPU 算物體與攝影機、GPU 算光線），
其他檔案不懂物理。要換度規（自旋、多洞）就是改這兩份。

## 2. 物理是怎麼算的

- **座標**：Kerr–Schild 形式（直角座標 x、y、z ＋ 向內的 Eddington–Finkelstein 時間 t）。
  `g_{μν} = η_{μν} + f l_μ l_ν`，史瓦西是 `f = rs/r`、`l_μ = (n, 1)`。這套座標在視界上是正常的，
  所以物體與攝影機可以一路算進視界裡面，不用換座標。
- **運動方程式**：哈密頓量 `H = ½ g^{μν} p_μ p_ν = ½(|p|² − p_t²) − ½ Σ f L²`，`L = n·p − p_t`。
  有質量的粒子 H = −½，光 H = 0。四階 Runge–Kutta。
- **攝影機**：每一格在攝影機的位置對度規做 Gram–Schmidt，得到它自己的局部標架（先對 4-速度投影，光行差就在裡面）；
  每個像素的方向換成光的動量，沿零測地線**往過去**追，直到飛到遠處（查天空）、貼到視界（黑）、
  或中途碰到吸積盤／物體。
- **物體**：發射時把整條測地線算好，存成一列浮點貼圖。光線自己帶著座標時間往回走，
  用「光經過那裡的那一刻」去查物體在哪 —— **光行時間差本來就在裡面**，
  「遠處看物體凍結在視界前」不是另外做的效果，是算出來的。
- **顏色**：吸積盤與物體的顏色用 `g = 觀察到的頻率 ÷ 發出的頻率 = 1/(p·u)` 調（都卜勒＋重力紅移）；
  盤的亮度乘 g⁴。色彩映射是示意（黑體色溫近似），不是光譜計算。

### 哪些是精確的、哪些是近似

| 項目 | 狀況 |
|---|---|
| 光線路徑、影子形狀、物體與攝影機的軌跡 | 史瓦西度規的測地線，數值積分；有自我測試對解析值 |
| 物體的光行時間差、凍結、時間變慢 | 直接由光線的座標時間算出，沒有另外加效果 |
| 吸積盤 | 幾何薄盤的溫度分布＋克卜勒轉速；「厚度」與雲的紋理是**美術**，不是流體模擬 |
| 物體的質量 | 測試粒子：路徑不看質量。質量只影響畫出來的大小、與「黑洞吃了變重」長多少 |
| 黑洞吃了物體變重 | 近似：物體過視界那一刻 rs 瞬間變大，其他東西從當下的位置與動量重算。真實情況不是瞬間的 |
| 攝影機的標架 | 每一格重新對著黑洞做，不是平行移動。徑向落下時兩者相同；帶角動量落下時等於一直把頭轉向黑洞 |
| 俯視圖上「你此刻看到的位置」 | 光行時間用「直線距離＋徑向光在視界附近多花的時間」估計；主畫面不用這個估計 |
| 星空、銀河 | 程序產生的，不是真的星表 |

## 5. 預留：多黑洞、自旋、融合（現在都沒做）

架構上留的位置，以及接下去會撞到什麼：

### 多黑洞（雙黑洞以上）
- **已經有的**：`holes` 是陣列；`physics.js` 的 `rhs`、`metricInv` 與著色器的 `rhs`、`stepLen`、抓捕判斷都對洞做迴圈
  （著色器的洞數上限是編譯期常數 `MAX_HOLES`，renderer 照 `holes.length` 現編）。
- **那是什麼近似**：把每個洞的 `f l l` 項直接加起來（Kerr–Schild 疊加）。它不是愛因斯坦方程式的解；
  兩個洞離得遠時是好的近似，靠近時不準。**沒有驗證過**。
- **要補的**：
  1. 介面與場景（現在只開放一個洞）。
  2. `shader.js` 的「用守恆量判斷」那條捷徑（`uEnergyTest`）只對單一靜態洞成立，多洞時要關掉 ——
     關掉之後，貼近視界的畫面會漏光（自我測試裡有量：同一格 1152 個像素）。要換別的做法，
     例如貼近視界時改用正規化過的變數積分，或把抓捕半徑放寬。
  3. 吸積盤、俯視圖的光行時間估計、攝影機「看向黑洞」都只認第 0 個洞。

### 自旋（Kerr）
- Kerr 在 Kerr–Schild 形式下只是換一組 `f` 與 `l`：
  `f = rs r³/(r⁴ + a² z²)`、`l = ((r x + a y)/(r² + a²), (r y − a x)/(r² + a²), z/r, 1)`，r 由隱式方程式解。
  要改的地方就是 `physics.js` 的 `rhs`／`metricInv` 與 `shader.js` 的 `rhs`（兩處都有註解標出來）。
- `hole.spin` 欄位、著色器的 `uHoleSpin` 已經在，但沒人讀；`hole.model = 'kerr'` 會被 `validateHoles` 擋下。
- **要補的**：`f`、`l` 對位置的導數（解析或差分）、視界半徑不再是 rs、
  `uEnergyTest` 的判斷要換（守恆量變成 E 與 L_z，再加 Carter 常數）、吸積盤的轉速與內緣（ISCO 隨自旋變）。

### 融合
- 需要會動的洞與隨時間變的度規。現在 `rhs` 假設度規不隨時間變（`dp_t/dλ = 0`、光線的 p_t 不更新）。
- **已經有的**：`hole.vel` 欄位；光線本來就帶著座標時間往回走；
  「度規變了之後，把還在飛的東西接到新的度規上」這條路已經走通（`bodies.replan`、`camera.renormalize`、
  `physics.normalizeMomentum`，現在給「黑洞吃了變重」用）。
- **要補的**：洞的位置寫成時間的函數（著色器裡要能查「光線那一刻洞在哪」，可以比照物體的軌跡貼圖）、
  `rhs` 的時間導數項、融合後的單一洞（質量與自旋）與重力波帶走的能量——這些要從數值相對論的結果查表，
  疊加近似在融合那一刻完全不適用。

## 6. 已知的限制

- 物體是測試粒子，彼此不互相吸引，也不會撞到吸積盤。
- 物體的像只在「攝影機此刻看到它的那個時刻」前後一段時間內找；離黑洞很遠的物體，
  繞過黑洞才到的第二個像（很小）可能不畫。
- 「黑洞吃了變重」之後，面板上的滑桿讀數會除以新的 rs 顯示，但滑桿本身還是原本的長度單位。
- 攝影機在視界內時，俯視圖的「看到的位置」只用直線距離估計。
- 很靠近奇異點（r < 0.02 rs）不算。

## 7. 這一版改動過程中抓到的錯（都已修）

| 症狀 | 原因 | 怎麼確認修好 |
|---|---|---|
| 換場景之後「物體／光束」按鈕失效 | 場景把拋射器的設定物件整個換掉，按鈕還抓著舊的 | 實際點按鈕發射光束：物體數 3 → 8（5 顆光子） |
| 「擦過光子球」的光卻掉進去了 | 發射方向用了座標上的角度，不是當地懸停的人量到的角度 | 設定 b = 1.03 b_c，量到 1.03000 b_c，飛走、最近 1.756 rs |
| 落下時影子裡出現白色斑紋（Tim 截圖） | 光線貼近視界時動量發散，單精度的 RK4 跨過去會算出垃圾，漏到天空 | 自我測試「貼著視界外（1.02 rs）」：1152 → 0；落下途中 3.2 rs 到 0.5 rs 抽 11 處，影子內亮點都是 0 |
| 物體「變成好幾顆」 | **不是錯**：重力透鏡的第二個像。量過單一物體穩定是 2 個像（大的在一側、小的在影子另一側） | 面板加了「畫出重影」開關與說明 |

著色器、renderer、bodies 是兩個模式共用的。戰鬥模式多用到的：

- **有人開的船**（物體種類 4）：軌跡不是測地線，是「到現在為止實際走過的路」，每一格接長；
  軌跡貼圖每個物體多兩列，放機頭、上方、引擎出力、被打中的閃光 —— 一樣照「光經過的那一刻」查。
- **每艘船自己一份格子**：飛船的 3D 貼圖切成 12 個船位（沿 z 疊 6 份、沿 y 疊 2 份），第 0 份是原本的模型，
  其餘每艘戰鬥中的船一份；被打掉的格子只重傳包住它們的那一小塊。每艘船另外帶一個「哪幾具引擎還在」的遮罩。
  顯示卡的 3D 貼圖夠大時 y 方向疊到 4 份（24 個船位）：第 1 份放彈藥的模型，其餘給船與破片。
- **一塊格子**（物體種類 6：破片、飛彈、動能彈）：跟船同一套沿線走格子，多一個 `uBodyE`（物體的位置對到模型座標的哪一點、一格多長），
  而且只走「包住它的那顆球」裡面那一段 —— 它只佔船位的一小角，不必把整個船位走完。朝向照軌跡貼圖的第三、四列（破片的翻滾、飛彈的機頭），
  沒給就是彈頭朝飛行方向。
- **光束**（物體種類 5）：見下面的表。不擋光，只把光加上去；遠的時候至少畫一個像素寬、亮度照比例降。
- **篩選**：每一小段光線對每個物體先看時段、再看「包圍球的球心離這一小段多遠」。戰鬥模式的小東西（光束、彈丸、飛彈、破片）
  從攝影機直直看過去離黑洞超過 4 rs 時，只交出「現在看到的那一刻」前後 2 的那一段路（包圍球小很多）；代價是它們沒有繞過黑洞的重影。

### 遊戲設定（不是物理）

- 船長 0.5 rs；主引擎 0.03 c²/rs（4.5 rs 以內光靠它懸停不住），加力 2.2 倍。
- 雷射：一發的光束持續 0.6、冷卻 0.55（都是船自己的鐘），所以按住就是連續的一道；一發要 9 點能量、每單位時間回 7，能量用完之後變成一節一節。
  打出半徑 3 格、深 50 格的洞。動能砲：出膛 0.45 c，坑的半徑 5 + 7·(γ−1)^⅓ 格（γ 是彈丸相對船的勞侖茲因子）。
  飛彈：出膛 0.15 c、最多 0.2 c²/rs、全力可推 8 的固有時；每隔一小段時間把自己與目標都照測地線推出去，朝「第一次最接近時差多少」修；炸掉半徑 14 格。
- 中彈的痕跡：洞口往外 0.9 格塗成燒紅的（色號 236，登記成會發光）、再往外到 2.4 格塗成燒黑的（73）。
- 破片：40 格以上才成一塊、一次中彈最多 4 塊（更小的直接不見），留 45 rs/c；小塊飛得快、轉得快。船毀時剩下的船身從最後中彈處一刀斷成前後兩截、
  比較大的那一截再縱向裂成兩塊。畫面上同時最多 10 塊（再多就把最舊的收掉）。中彈另外噴 1～3 顆燒紅的碎屑（小方塊，純裝飾）。
- 部位在 `js/world.js` 的 `PART_DEFS`：反應爐、駕駛艙剩不到 50% 算壞（船毀），武器 40%，引擎 50%；玩家的門檻乘 0.3。
  船身剩不到一半、或武器全壞也算毀。清完一波，玩家的船修回原樣、飛彈補滿。
- 邊界：r > 140 rs 之後多一個朝黑洞的固有加速度 0.004 × (r − 140)。平直空間以 0.6 c 衝進去，掉頭的地方是 R + √(2(γ₀−1)/k) = 151.18 rs（自我測試對這個值）。
  它是軟的：0.9 c 加上全程加力可以衝到 R 外面約 47 rs 才掉頭。戰場直徑 280，所以每艘船的歷史留 420 rs/c。
- 自動飛行：維持圓軌道；目標看得到、夠近就待在同樣高的軌道，否則換到 0.78 倍半徑的軌道（角速度不一樣，才繞得到同一側）；
  機頭轉到「接下來能射的那一種」的射擊解上。自動開火：哪一種對準了、能射就射。敵機用的是同一套射控，另外加瞄準誤差。
- 進了視界之後畫面自動放慢（剩下的路照自己的鐘不到 1 rs/c）。

### 已知的限制

- 破片只是看得到：不擋子彈、彼此不會撞、不受外圍的空間扭曲影響。玩家的船毀了之後時間就停了，所以看不到自己的船斷開。
- 畫面上船身的洞照「看到那艘船的時刻」出現（光直線飛過來的時間）；繞過黑洞的第二個像會跟著同時出現洞。
- 鏡頭外的小東西（光束、彈丸、飛彈、破片）不交給著色器；靠近黑洞的不篩。加上上面「篩選」那一條，從黑洞另一側繞過來的小東西的像可能少畫。
  量到的（RTX 2060，946×713）：正前方同時有 45 道光束時一格 6～12 ms，只有船的時候 1.4 ms。物體上限 48 個，滿了先丟最舊的小東西。
- 敵機標記沒有算光被黑洞彎：視線擦過黑洞 3.2 rs 以內時標成虛線。
- 船上還沒有看得出來的砲管（射出去的飛彈與動能彈有模型了）；部位是照餘暉號的外形劃的方盒。
- 光束每一段（約 0.6）之內是直的：按住開火又一邊急轉的時候，光束是折線（每個折點都接得上，沒有縫）。
  一段光束如果第一顆光子沒打中、後半才掃到目標，那一段在畫面上會穿過目標（命中只看每一段的第一顆光子）。

## 9. 星空（2026-11-13）

Tim：「目前背景的星空 好像是立方體分布的?(希望改為球體 且可以參考現實星空)」。原本是把天球投到立方體六個面、每格放一顆，看得出格子。

- 現在用耶魯亮星表第五版（CDS V/50，9,096 顆）：`tools/stars_pack.py` 轉成 `js/stars_data.js`（每顆 6 bytes），`js/stars.js` 解碼。
- 天球怎麼擺：赤道座標 → 銀河座標（標準矩陣）→ 模擬座標，北銀極對到著色器畫銀河用的法線。
  驗證：轉檔時拿星表自己附的銀經銀緯對過（中位數差 0.004°，最大 0.094° 是 61 Cyg 這幾顆自行很大的星）；
  參宿四與參宿七在模擬座標裡的夾角 18.6054°，球面三角算的是 18.6058°；行列式 +1（不是鏡射）。
- 著色器怎麼查：立方體六個面各 28 × 28 格、每格最多 28 顆，一顆星放進它的光暈碰得到的每一格 ⇒ 每個像素只讀一格。
  格子只是查表用的。每顆星在自己的方向與光暈邊緣共 9 個方向都查得到自己：81,864 次裡查不到 27 次（有 3 次是格子滿了）。
- 顯示卡驗證：把黑洞拿掉、正對天狼星，最亮的點離畫面正中間 0.0005 個像素；鏡頭轉 4° 之後離預測位置 0.02 個像素；把星表拿掉那裡就不亮。
- 真的星往銀河面集中：銀緯 ±10° 以內佔 26.4%（均勻的話 17.4%；換一個無關的平面數是 16.5%）。
- **不是真的部分**：比星表暗的那一層（亂數，在球面上均勻撒再照銀緯篩）、銀河的雲氣（雜訊）、亮度的壓縮（星等差 5 等只差 10 倍）、黑洞相對銀河的朝向。
